## 摘要

這是一個功能完整、UI 精緻的單檔案 PWA。為了進一步提升 **開發效率** 與 **資料分析能力**，本計畫將規劃系統性的架構升級。基於小規模熟人使用的友善情境，我們將優先投入於架構現代化與功能擴充，並在後期逐步完善安全性加固。

實作時請務必參考 [實作注意事項](./implementation-considerations.md) 以確保功能完整性，並以 [驗收標準](./acceptance-criteria.md) 作為結案依據。

> **註**:雖然安全性加固整體放在 Phase 3,但有少數「順手做幾乎不花時間、之後做反而要重做兩次」的衛生項目(例如 `.gitignore` 排除 `.env`、CSP meta tag、SRI hash、統一 `esc()` 用法),會直接整合進 Phase 1 的重構工作中,見 §2 Phase 1.5。

本文件依優先級分為四個 Phase:

| Phase | 主題 | 預估工時 | 優先順序 |
|---|---|---|---|
| Phase 1 | 程式碼結構重構 | 2–4 週 | 🌟 優先 (提升開發效能) |
| Phase 2 | 資料模型正規化與功能擴充 | 3–6 週 | 📈 高 (價值極大化) |
| Phase 3 | 安全性補強 | 1–2 週 | 🔒 中 (穩定性基礎) |
| Phase 4 | 使用者體驗與工程實踐 | 持續 | 🎨 低 (精益求精) |

## 一、現狀分析

### 1.1 程式碼結構優化空間 (🌟 優先)

| # | 現狀說明 | 優化目標 |
|---|---|---|
| C1 | HTML / CSS / JS 整合於單一檔案 | 提升閱讀性、便於協作、增強 IDE 提示 |
| C2 | 內嵌 base64 圖示致檔案體積較大 | 提升載入速度，善用瀏覽器快取機制 |
| C3 | 廣泛使用 `onclick="..."` 內聯處理器 | 提升程式碼維護性與重構彈性 |
| C4 | 全域變數管理 (如 `sb`、`members`) | 提升狀態追蹤精確度，減少 side-effect |
| C5 | 尚未引入 build / bundle 機制 | 對接現代前端工具鏈 (如圖表庫、狀態管理) |

### 1.2 資料模型升級潛力 (📈 高)

| # | 現狀說明 | 優化目標 |
|---|---|---|
| D1 | 資料集中於單一 `data` jsonb 欄位 | 支援標準 SQL 查詢，增強資料一致性約束 |
| D2 | Read-modify-write 資料處理模式 | 提升併發寫入時的資料完整性 (Race Condition 預防) |
| D3 | 月份 key 採用 0-indexed 字串 | 統一時間計算邏輯，簡化開發直覺 |
| D4 | 數據追蹤以條列顯示為主 | 增強趨勢分析能力，產出直觀的變化曲線 |

### 1.3 安全性優化考量 (🔒 中 - 依需求調整優先級)

| # | 現狀說明 | 優化目標 | 處理時機 |
|---|---|---|---|
| S1 | Supabase anon key 存放於前端 | 提升 Key 管理的隱蔽性 | Phase 1.5(部分) + Phase 3 |
| S2 | 會員密碼存放於 jsonb | 升級至專業的身份驗證系統 | Phase 3 |
| S3 | 管理員 PIN 存於 `localStorage` | 提升管理權限的驗證強度 | Phase 3 |
| S4 | RLS 權限配置 | 實施更細粒度的資料存取控制 | Phase 3 |
| S7 | `innerHTML` + 部分欄位未經 `esc()` 轉義 | 預防 XSS,統一輸入處理 | Phase 1.5(順手做) |
| S9 | 缺少 CSP / SRI hash | 加固 CDN 與第三方資源信任邊界 | Phase 1.5(順手做) |

### 1.4 功能與 UX 提升空間 (🎨 低)

| # | 現狀說明 | 優化目標 |
|---|---|---|
| F1 | 月份範圍採用固定配置 | 升級為自動產生的動態日期範圍 |
| F2 | 數據顯示以現狀為主 | 增加視覺化趨勢分析，提升數據價值 |
| F3 | 網路依賴性較高 | 引入 Service Worker，強化離線使用體驗 |

## 二、升級計畫

### Phase 1 — 程式碼結構重構 (🌟 2–4 週)

> 目標：將開發模式從「傳統單檔案」升級至「現代模組化架構」。維持現有 UI 與功能，進行核心重構。

**1.1 建立現代化開發環境 (Vite)**
- 任務
  - 初始化 `package.json`，引入 Vite 工具鏈
  - 建立專業資料夾結構 (`src/`, `public/`)
  - 使用環境變數 (.env) 管理專案配置
- 優化點：C5、E3

**1.2 模組化拆分**
- 任務
  - 抽出 CSS 至獨立樣式表，按功能模組管理
  - 抽出 JS 邏輯至獨立模組 (Auth, Members, InBody, Utils)
  - 將內嵌圖示轉為獨立資產檔案
- 優化點：C1、C2

**1.3 事件處理優化**
- 任務
  - 改用監聽器 (EventListener) 集中管理交互邏輯
  - 實作結構化的狀態管理模式
- 優化點：C3、C4

**1.4 工程標準建立**
- 任務
  - 引入 ESLint 與 Prettier 自動化格式工具
  - 自動產生資料庫型別定義，提升開發安全性
- 優化點：E2、C10

**1.5 重構衛生 (順手做的基本防線)**
> 這些項目嚴格說屬於安全性,但因為:**(a) 在 Phase 1 重構時順手做幾乎不花時間,(b) 延後到 Phase 3 才做意味著要回頭再改一次相同的檔案**,因此提前在 Phase 1 完成。

- 任務
  - **`.gitignore` 排除 `.env`**:當 1.1 把 anon key 從 `index.html` 抽到 `.env` 時,務必同步把 `.env` 加入 `.gitignore`,避免 key 被 commit 進公開 repo
  - **加上 CSP meta tag**:在 `index.html` 加一行 `<meta http-equiv="Content-Security-Policy" content="...">`,限制 script-src / img-src 來源
  - **加上 SRI hash 給 CDN script**:`<script src="...supabase-js@2" integrity="sha384-..." crossorigin="anonymous">`,或考慮改為 npm 安裝後由 Vite bundle(更好)
  - **統一 `esc()` 用法**:重構 `innerHTML` 時,把目前 audit 出來零星沒走 `esc()` 的欄位都補上;改寫成 DOM API 後此問題自然消失
  - **補上 `.editorconfig`**:統一縮排規範
- 優化點:S1 (部分)、S7、S9、E2

---

### Phase 2 — 資料模型正規化與功能擴充 (📈 3–6 週)

> 目標：極大化資料分析價值，實作核心「趨勢圖表」功能。

**2.1 資料庫架構升級**
- 任務
  - 設計專業的 InBody 紀錄表與運動紀錄表
  - 實作資料平滑遷移 (Migration) 流程
- 優化點：D1、D3

**2.2 實作趨勢視覺化 (Trends)**
- 任務
  - 引入專業圖表庫 (如 Chart.js)
  - 新增「趨勢分析」介面
  - 呈現體重、體脂率等關鍵指標的演進曲線
- 優化點：F2

**2.3 自動化日期邏輯**
- 任務
  - 根據目前時間自動產出月份選項，提升系統靈活性
  - 統一日期計算標準
- 優化點：D4、F1

---

### Phase 3 — 安全性加固 (🔒 1–2 週)

> 目標：在架構穩健後，進一步強化系統防護力。

**3.1 專業授權系統遷移**
- 任務
  - 啟用 Supabase RLS (Row Level Security)
  - 遷移至官方 Auth 認證流程
- 優化點：S1、S2、S4

**3.2 資源權限細分**
- 任務
  - 強化 Storage bucket 安全規範
  - 提升管理權限的後端驗證機制
- 優化點：S3、S8

---

### Phase 4 — 使用者體驗與工程實踐 (🎨 持續)

- **離線支援能力**: 實作 Service Worker 強化穩定性。
- **多語系支援**: 建立 i18n 機制以便未來擴展。
- **自動化部署**: 建立 GitHub Actions 流程，實現 push 即更新。
- **品質驗證**: 為核心邏輯加入單元測試，確保系統長期穩定。

                            │
                            ▼

**第一個 Sprint (2 週) 聚焦重點**:
1. 建立 Vite 現代化開發目錄。
2. 進行 HTML、CSS、JS 的邏輯解耦。
3. 最佳化圖示資產載入機制 (預計提升載入效率)。
4. 完成 Phase 1.5 重構衛生項目(`.gitignore` 排除 `.env`、CSP、SRI、`esc()` 統一)——隨重構順手帶,不另列工時。

## 四、風險管理與決策

1. **開發模式轉型**: 採用「開發時模組化、發布時自動優化」的策略，兼顧維護與效能。
2. **技術選型**: 優先保持純粹的 Vanilla JS 以降低複雜度，後續視 UI 需求彈性評估框架引入。
3. **資料遷移**: 遷移前進行完整資料備份，確保服務持續性。
